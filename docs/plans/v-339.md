# Plan: v-339 (issue #339, storage fault tests)

## What is open

The latest verification comment lists both criteria as unmet: no test limits
the coordinator's file size, makes its state directory read-only while it
runs, or kills it during a burst of writes; so nothing checks that each
failure the coordinator reports names what failed and what to do.

## What I found in the code

- `Store::commit_with_snapshot` (`src/store.rs`) applies events to a copy of
  the state and replaces the in-memory state only after `transaction.commit()`
  succeeds, so a failed write leaves memory and file in step. Nothing changes
  there.
- A store error reaches the client as `storage_error` with SQLite's bare
  text (`src/daemon.rs`, the `Err(e)` arm of `answer`): for a full disk,
  "database or disk is full". It says what failed, vaguely, and not what to
  do. The hook turns any refused call into no decision plus a stderr
  diagnostic (`Failure::Rejected` → `Reply::none("unknown", detail)`), so the
  daemon's message is what the agent's host shows.
- Rust ignores SIGPIPE but not SIGXFSZ: a coordinator over its file-size limit
  is killed by the signal before a write can fail. The test starts it through
  `sh -c 'ulimit -f N; trap "" XFSZ; exec …'`, so writes past the limit fail
  with EFBIG, the same path as ENOSPC on a full disk (`ulimit` and `trap` are
  POSIX and work on Linux and macOS; an ignored signal stays ignored across
  `exec`). I won't change the daemon's signal handling here.

## Changes

1. `tests/storage_faults.rs` (new), `#![cfg(unix)]`. Each test starts a real
   coordinator process; the subject is how the OS, SQLite's write-ahead log
   and the process behave under a storage fault, which no in-process test
   can show.
   - `a_coordinator_over_its_file_size_limit_answers_the_hook_and_reopens_intact`:
     start once without a limit, register a workspace, then stop; restart with
     `ulimit -f` just above the store's current size; issue writes
     (workspace registrations) until one is refused. Check that the refusal is
     `storage_error` naming the state directory and what to do; a Claude
     `PreToolUse` hook run answers within its budget (exit 0, the diagnostic
     carries the same text); after a stop, `Store::open` replays,
     `PRAGMA integrity_check` is `ok`, and every acknowledged registration is
     in the state.
   - `a_state_directory_made_read_only_while_running_answers_the_hook_and_reopens_intact`:
     chmod the state directory (and its files) read-only while the coordinator
     runs; run hooks and writes. Each answers within its budget, and each write
     either succeeds or is refused naming what failed and what to do. A
     restart in the read-only directory fails with a message that names the
     directory and the fix. Restore the mode; the store reopens intact with
     every acknowledged write. If the test runs as root (permissions not
     enforced), it prints a `skipped:` line instead.
   - `sigkill_during_a_burst_of_writes_loses_no_acknowledged_event`:
     several threads send distinct registrations; SIGKILL the coordinator once
     some are acknowledged. On reopen: integrity `ok`, every acknowledged one
     is in the state and has its event and receipt, and no receipt or event
     exists without the other (nothing partial). A restarted coordinator
     answers status.
2. `src/daemon.rs`: the `storage_error` message from `answer` (and the same
   arm in `events_for_client`) says that the coordinator could not read or
   write its store at the state directory, gives SQLite's reason, and says
   what to do: free disk space or make the directory writable, then retry;
   a write that failed was not recorded. One helper, used by both arms.
   If the read-only restart's start-up error lacks the directory or the fix,
   fix that message in `src/daemon.rs` too.
3. `scripts/ratchets/baseline/src/daemon.rs.tsv`: tighten if `daemon.rs`
   changes its measured sizes (`--tighten`/`--record`).
