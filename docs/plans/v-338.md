# Plan: v-338, nightly fuzz targets (first slice of #338)

Issue #338 lists about a dozen parsers plus one `langspan_graph::extract`
target per language. All of it in one pull request would go well past the
300-line budget, and half of the parsers are private, so they need a
`fuzzing` feature in the main crate. This pull request lands the first
independent slice: the `fuzz/` crate, the nightly job, and targets for every
listed parser that the crate already makes public. It says "Refs #338" and
lists the rest under "Not done yet".

## Targets in this slice (all public today, no source change)

| Target | Entry point | Seeds |
| --- | --- | --- |
| `socket_frame` | `protocol::read_frame`, then `serde_json::from_slice::<protocol::Request>` | `fixtures/request-v*.json`, a few `*-command-v10.json`, newline-terminated |
| `index_import` | `index_file::parse_header` on the first line, `parse_record` on the rest | a header line and file records shaped as the export writes them |
| `test_output` | `test_output::read` (both `cut` values) | short cargo, go test and pytest output |
| `codex_patch` | `codex::patch_paths` and `codex::patch_edits` (the Codex host's patch parser) | the patch text from `fixtures/codex-0.171.0` and `fixtures/codex-contract` |
| `graph_rust`, `graph_python`, `graph_typescript`, `graph_tsx`, `graph_go`, `graph_java`, `graph_csharp` | `langspan_graph::extract(Language::X, data)` | a small source file per language |

Each target only calls the parser and drops the result: the oracle is "no
panic, no abort, no sanitizer report, no timeout".

## Not in this slice (needs the `fuzzing` feature in `src/`)

The host event parsers (Claude Code, Cursor, Antigravity, Codex event JSON),
the reformat tokenizer (`mod reformat` is private), the Git plumbing parsers
in `src/observer.rs`, the dashboard HTTP head parser and the teammate state
payload in `src/remote.rs`. The next slice adds a non-default `fuzzing`
feature that re-exports them, and the targets for them.

## Files

- `fuzz/Cargo.toml`: a package with its own empty `[workspace]`, so it is
  outside the main workspace and the root `Cargo.lock` doesn't change.
  Depends on `langspan`, `langspan-graph`, `serde_json` (same pin) and
  `libfuzzer-sys`.
- `fuzz/Cargo.lock`: committed, so the nightly job builds with `--locked`.
- `fuzz/.gitignore`: `target/`, `artifacts/`, `coverage/`, and the corpus
  entries libFuzzer adds at run time are not committed (the job runs on a
  copy).
- `fuzz/README.md`: how to run one target locally.
- `fuzz/fuzz_targets/*.rs`: the 11 targets above.
- `fuzz/corpus/<target>/*`: committed seeds.
- `.github/workflows/fuzz.yml`: nightly at a fixed hour, `workflow_dispatch`,
  and on pull requests that change `fuzz/**`, the workflow or `Cargo.lock`.
  One job on a pinned nightly toolchain with pinned `cargo-fuzz` builds every
  target once (a matrix would build the whole crate eleven times), runs each
  for 180 s (`-max_total_time`) on a copy of its seeds, keeps going after a
  failure, and uploads `fuzz/artifacts/` when one fails. A `nightly-report` job with only `issues: write`, which checks
  out nothing, opens or comments on the existing nightly issue ("Nightly
  Rust checks on main failed"), the same way `coverage.yml` does, naming the
  run and the artifact.
- `docs/dependencies.md`: a row for `libfuzzer-sys` (fuzz crate only, not
  in the release build).
- `docs/engineering.md`: one Commands line for fuzzing.
- `docs/security/threat-model.md`: a sentence that the fuzz workflow's only
  write permission is `issues: write` in a job that runs no repository code.

No shared contract (protocol, CLI dispatch, daemon, generated tables)
changes. The ratchets don't scan `fuzz/`.

## Order and checks

1. Write the crate and one target (`socket_frame`); `cargo +nightly fuzz
   build` and `cargo fuzz run socket_frame -- -runs=0` on the seeds. Check
   `git diff --exit-code Cargo.lock`.
2. Break the guarded property once: a target that panics on a seed byte
   must fail `cargo fuzz run` and leave a crash file in `fuzz/artifacts`,
   which is what the workflow uploads. Revert.
3. Add the other targets and seeds; run each for a short time locally.
4. Workflow; `zizmor .` clean.
5. Docs. Then `cargo fmt`, clippy, full `cargo nextest run`, doc tests;
   root `Cargo.lock` unchanged.

## Follow-up: install cargo-fuzz reliably (after #541)

The merged job fails while installing cargo-fuzz 0.13.1: it builds the tool
with `cargo +"$FUZZ_TOOLCHAIN" install --locked`, and on that nightly the
`rustix` in cargo-fuzz's own lockfile detects a nightly compiler, enables
`rustc_attrs` and fails ("attributes starting with `rustc` are reserved",
`rustc_layout_scalar_valid_range_*`). The nightly date is already pinned
(`FUZZ_TOOLCHAIN: nightly-2026-11-26`), so the break is in how the tool is
built, not in our targets.

cargo-fuzz itself needs no nightly; only `cargo fuzz build` and `run` do. The
fix is option (1) of the task: build the tool with `--locked` (its own
lockfile) on the repository's pinned stable toolchain (`rust-toolchain.toml`,
1.100.0), and keep the pinned nightly for building and running the targets.

- `.github/workflows/fuzz.yml`: split the step into "install the pinned
  nightly" and "install cargo-fuzz", the second as plain
  `cargo install --locked cargo-fuzz --version 0.13.1` (no `+nightly`), with
  a comment saying why. Keep `FUZZ_TOOLCHAIN` pinned to a date.
- `docs/plans/v-338.md`: this section.

Checks: a local `cargo install --locked cargo-fuzz --version 0.13.1` on the
pinned stable into a temporary root; `zizmor .`; a manual
`gh workflow run fuzz.yml --ref ci/v-338-fix` that installs the tool, builds
every target and runs each one. No shared contract, Rust source, lockfile or
docs table changes.
