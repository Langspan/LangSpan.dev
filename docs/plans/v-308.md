### Why 6 and 15 fit, and where they don't

- **Merge queue, 15.** The slowest build job measured cold (`cold=true`,
  nothing restored) took 12m43s on macOS and 11m15s on Linux
  (`docs/evidence/ci/balance.md`). A warm build takes about 4.5 minutes.
  Shards are already at 15. Main and nightly stay at 30, because nightly
  also builds the release binary.
- **Pull request, 6.** A warm Linux fast-lane job takes about 3.7 minutes. A
  lockfile change falls back to main's latest entry and rebuilds only the
  changed crates. The one case that doesn't fit is a change to
  `rust-toolchain.toml`: no cache entry exists for the new toolchain, so the
  build is cold (about 11 minutes). A job-level `timeout-minutes` can't read
  step outputs or `hashFiles`, so the workflow can't detect that case before
  the job starts. The docs and the pull request name this exception, and the
  pull request asks the owner how a toolchain bump should land: a temporary
  limit change in that pull request, or an admin merge. I won't add
  machinery for the exception without the owner's answer.

- The 9 `dry_run_*` tests in `tests/benchmark_harness.rs`. The full lane
  skips them unless the change touches the paths that `ci-changes.sh` lists.
  The nightly run always runs them.

  (`LANGSPAN_CHECK_RELEASE` is true only on `schedule`).
- No other test is nightly-only: every test runs in exactly one shard of the
  full lane (#483).
